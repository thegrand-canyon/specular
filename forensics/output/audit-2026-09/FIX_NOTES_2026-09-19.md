## Per-finding

### F-01 (HIGH) — NFT transfer froze `repayLoan` / `liquidateLoan`
**Root cause.** Both closing paths called the reputation manager with `loan.borrower` (address). ReputationManagerV3
resolves `addressToAgentId(borrower)` and reverts `Not an agent` once the registry has deleted that mapping on transfer.

**Fix.** Resolve the agent by **`loan.agentId`**: `holder = agentRegistry.ownerOf(loan.agentId)` is passed to
`recordLoanCompletion` / `recordDefault`. `AgentRegistryV2._update` sets `addressToAgentId[to] = tokenId` on every
mint/transfer and the registry has no burn and no other writer of that mapping (`setAgentWallet` only touches
`agentWallet`), so `addressToAgentId[ownerOf(id)] == id` is a registry invariant — the call can no longer fail because
of where the NFT went. ReputationManagerV3 did not need a `…ById` variant.

**Repayer policy (design choice).** `repayLoan` accepts `msg.sender == loan.borrower` **or** `msg.sender == ownerOf(loan.agentId)`.
Rationale: the original borrower received the principal and must always be able to close; after a legitimate sale the
buyer holds the agent whose reputation the open loan affects and may want to clear it. Anyone else: `"Not the borrower"`
(reason string unchanged). `liquidateLoan` stays `onlyOwner` and never depends on the borrower address being registered.

**Collateral (design choice).** Always returned to **`loan.borrower`** — the address that posted it. An NFT transfer
moves identity, not USDC escrowed for a specific wallet; a holder who repays is settling the agent's debt and must
arrange collateral with the seller off-chain. There is no theft vector either way (repaying costs principal + interest
for collateral ≤ principal), so the choice is purely about not silently re-assigning one wallet's escrow to another.
Reputation (bonus / default penalty) lands on the **agentId** — i.e. on whoever holds the NFT — as the model intends.

### F-02 (MEDIUM) — top-up forfeited the whole position's in-flight interest
**Root cause.** `supplyLiquidity` re-stamped `depositTimestamp` for the entire position on every supply (W1 sandwich
defence), so a 1-base-unit top-up disqualified all pre-existing principal from every open loan.

**Design: two tranches per position, bounded active-loan set.**
- `LenderPosition` is unchanged in shape; `amount` remains the TOTAL principal and `depositTimestamp` becomes the
  **base tranche's** stamp. A new packed mapping `pendingTranche[agentId][lender] = {uint128 amount, uint128 timestamp}`
  holds the part of `amount` that was topped up while loans were open (invariant `pending ⊆ amount`).
- Qualified principal for a loan started at `S` (new view `qualifiedAmountAt`):
  `(depositTimestamp <= S ? amount − pending : 0) + (pending.timestamp <= S ? pending : 0)`.
- `activeLoanIds[agentId]` (≤ `MAX_ACTIVE_LOANS_PER_AGENT` = 10, pushed at disburse, swap-and-popped at close) lets
  `supplyLiquidity` decide **losslessly** what to do with a top-up:
  | case | condition | action |
  |---|---|---|
  | (a) | `amount == 0` or no loan in flight | single base tranche stamped now (W1 defence intact) |
  | (b) | no pending tranche yet | base untouched; new money → pending stamped now |
  | (c) | no ACTIVE loan started in `[base.ts, pending.ts)` | fold pending into base (base keeps its stamp); new money → pending |
  | (d) | no ACTIVE loan started in `[pending.ts, now)` | merge new money into pending and re-stamp |
  | (e) | otherwise | **revert** `"Top-up would forfeit in-flight interest"` |
  (c)/(d) are provably lossless (the tranche being merged is qualified for exactly the same active loans before and
  after). Case (e) would need a third tranche; rather than silently forfeit (V6) the top-up is refused until the older
  in-flight loans close — `canTopUp(agentId, lender)` exposes this for the SDK/MCP. A new lender is never refused.
  Rejected alternatives: weighted-average timestamp (re-admits JIT capital, re-opens W1); per-loan per-lender snapshots
  (O(lenders) SSTOREs per `requestLoan`); unbounded tranches (unbounded `_distributeInterest`).
- `withdrawLiquidity` draws the **pending tranche first (LIFO)** — a top-up-then-withdraw round trip leaves the base
  qualification untouched and can never grant qualification (base stamps only ever move forward).
- `_socializeLoss` shrinks pending pro-rata with the position (`cut = share·pending/amount`, clamped) so `pending ⊆ amount`
  survives losses; the loss itself is still exactly `min(loss, Σ principal)`.
- `_distributeInterest` is still two passes over ≤ 50 lenders, O(lenders); per-lender qualified amounts are cached in
  memory between passes. Extra cost: one packed SLOAD per lender.
- `seedPosition` clears any pending tranche (seeded positions are one base tranche).

### F-03 (MEDIUM) — late repayment cost nothing
**Fix.** `repayLoan` charges interest on **`max(duration, elapsed)` capped at `duration + LATE_INTEREST_CAP` (30 days)**
at the rate locked at request (`_interestDue`). Early/on-time repayments are unchanged (nominal term). Lateness is
recorded on-chain — `repayments[loanId] = {repaidAt, interestPaid, lateSeconds}`, `lateRepayCount[agentId]`,
`lateSecondsTotal[agentId]` — and `LoanRepaidLate(loanId, agentId, lateSeconds, lateInterest)` is emitted. A late repay
still earns no reputation bonus (`onTime=false`).
**Reputation penalty:** ReputationManagerV3 exposes no late-repayment hook (only `recordDefault`, which would
mis-record a repaid loan as a default and bump `defaultCount`), and the task ruled out changing it unless strictly
necessary. So the economic penalty is on-chain now and the reputation penalty is left for a ReputationManager
revision (needs its own redeploy) that can consume `repayments`/`lateRepayCount`. THREAT_MODEL.md (I-6) should say so.

### F-05 (LOW) — loss > Σ principal stranded unclaimed interest
**Fix.** `liquidateLoan` runs a second pass, `_socializeInterestLoss`, over `earnedInterest` for `loss − reduced`
(exact, floor remainder assigned, no dust), emitting `InterestLossSocialized(agentId, amount)`. Because
`availableLiquidity + totalLoaned == Σ amount + Σ earnedInterest` held before the liquidation, the excess is always
absorbable and the per-pool conservation stays **exact**, so every remaining claim is backed and `claimInterest` is no
longer first-come-first-served. Lenders left with 0 principal **and** 0 interest are pruned from `poolLenders`
(`_pruneEmptyLenders`, index-based swap-and-pop) so wiped-out slots are not leaked (H-2 hygiene). Side effect: audit
note I-2 (`resetPoolAccounting` re-creating phantom liquidity after such a liquidation) no longer applies — the rebuilt
`availableLiquidity` now equals the true backing. Unclaimed interest remains lendable by design (unchanged).

### F-07 (LOW) — deactivation was a no-op
**Fix.** `requestLoan` and `createAgentPool` require `agentRegistry.isAgentActive(msg.sender)` → `"Agent deactivated"`.
`repayLoan`, `liquidateLoan`, lender `withdraw`/`claim` are deliberately **not** gated (closing and exit paths stay live).
`supplyLiquidity` into an existing pool of a deactivated agent is also not gated (lenders' choice; the agent cannot
borrow it) — say if you want that gated too.

### F-06 (LOW) — no code change
`setMinSupplyAmount` cap is `<= 100 * 1e6` (line unchanged); the lever can be set to 100 USDC today.
